# Plan — the owner's seven of 2026-10-21

Findings first (what is really broken, what is working as built), then the
build plan and the questions that need an answer before building.

## Findings

### 1. PO paper: the CEO signs an importation order as "Purchasing Manager" — REAL
`approvalSlots()` labels every slot with the step's NAME (`shared/approvals.ts:1546,
1554, 1566`), and the PO route's step 1 is seeded "Purchasing Manager"
(`seed.ts:314, 323`). The importation twin (`IMPORTATION_ROLES`) only changes who
may sign (`stepRoleId`, `:182-189`), never the label. Two consequences on an
importation order:
- Carter prints under "PURCHASING MANAGER" (Pic 1).
- Over ₱100,000 he also co-signs step 2 "CEO / President" in the same `act()`
  (`:938-990`), and the PO paper (`procurement.ts:4250-4259`) has no
  `onePerPerson`, so he prints twice at the same instant — three times if he
  prepared it.
The Incoming paper (`warehouse.ts:1520`) has the same label rule.

### 2. Activity responses have no reason — NOT BUILT
`SalesActivityInvitee` holds `response` and `respondedAt` only (`schema:1972-1989`);
`POST /activities/:id/respond` takes `{ response }` alone (`sales.ts:3673`). The
meetings' minutes already have the pattern (`POST /meetings/:id/minutes/respond
{ response, comment }`, `meetings.ts:783-797`).

### 4. Memos — list is WORKING AS BUILT; the rest is NOT BUILT
- "Didn't show on the list": the screenshot is `/g-hr/memos?scope=mine` and
  **Mine = memos I DRAFTED** (`memos.ts:137-159`, the CSV calls it "drafted by
  me"). JR received it and drafted nothing, so Mine and all four cards read 0.
  Under **All** (a View All holder) it is listed; a recipient without the
  register right reads it on My Records › Memos Received and on its own page.
  So: not a bug, but the Mine switch is misleading on this register — see the
  plan.
- Pull back / delete an issued memo: refused today — `'Only a draft is deleted
  — an issued memo is archived'` (`:419`); archive only (`:494-511`).
- A recipient's reply / explanation: no field, no route (`MemoRecipient` =
  `acknowledgedAt` only, `schema:6063-6074`).
- Acknowledgement stamp on the paper: HR's copy prints the DATE only
  (`formatDate`, `:596`), never the time; the recipient's own copy prints
  nothing about their acknowledgement (`:582`, `register` only).

### 5. Insights sidebar wraps with no icon — REAL
Insights declares no `group`, so `Shell.tsx` takes the flat path (`:590-609`),
which renders a bare `<span>` — no `<Icon>`, no `.nav-label` (the class that
gives `nowrap` + ellipsis, `styles.css:4276`). Collapsed, the rail hides
`.nav-label` but not the bare span, so the words are squeezed (Pic 4).

### 7. Cancelled sales order cannot be deleted — REAL (a 500)
`DELETE /sales-orders/:id` (`salesOrders.ts:1380-1396`) passes the right, the
author check and the status check for a CANCELLED order, then runs a BARE
`prisma.salesOrder.delete` — not through `deleteOrRefuse()`. Seven relations
are `Restrict` whatever their status: `Invoice`, `InvoiceRequest`,
`CommissionRequest`, `PurchaseRequest`, `PurchaseOrder`, `StockIssue`,
`PulloutSlip`. GT-SO-2026-0005 carries S.I. 1435 / D.R. 1278, so an invoice
(or invoice request) almost certainly names it → Prisma P2003 → "Something went
wrong on our side". Cancel never checked invoice requests or commission
requests, so a live request can still stand on a cancelled order.

### 3 and 6. Asset Management and Hiring — NOT BUILT, no footing
No model for company property issued to an employee (the clearance checklist
has it as hand-typed rows; `BorrowSlip` is short-term warehouse lending by
quantity with a due date, not a tagged unit on long-term issue). Nothing for
manpower requests, applicants, exams or contracts. `Position` (the Plantilla)
and `POST /employees` are the two seams a hire lands on.

## The plan — three pushes

### Push 1 — the fixes (1, 2, 5, 7, and the memo items)

**1. PO / Incoming paper labels the signer by the capacity he signed in.**
In `approvalSlots()`: when `request.importation` and the step's role has a twin
in `IMPORTATION_ROLES`, the slot's `step` becomes the twin role's NAME
("Purchasing Manager (Import)") — and when the signer (or the single assignee
on an open/draft step) holds `ceo`, it becomes the CEO step's name
("CEO / President"). The query at `:1530` selects the step's `roleId`; the draft
path uses `st.approvers`. Then the PO paper applies `onePerPerson(slots,
po.createdById)` keeping the LATER (CEO) slot where one person signed both
steps, so Carter prints once, as CEO / President, with one timestamp. Incoming
gets the same. verify-chain: an importation PO signed by a `ceo` holder prints
"CEO / PRESIDENT" once, a non-CEO import PM prints "PURCHASING MANAGER
(IMPORT)".

**2. A reason on an activity response.** `SalesActivityInvitee.comment`
(nullable); `POST /activities/:id/respond { response, comment? }` — required
for DECLINED (the organiser is owed the why, as Return / Reject are), optional
otherwise; kept on every read; the page's Not going button asks in the confirm
bar (rule 19), Going / Maybe take an optional note; the Responses table gains
the comment under the name; the bell to the organiser carries it
("Maria is not going: on leave that day"). The email's `?respond=DECLINED` link
opens the page with the bar open rather than recording blind. verify-calendar.

**5. Insights sidebar.** Give the flat path `.nav-label` and an `<Icon>`:
`SECTION_ICONS` is keyed by group name, so add a per-screen icon map keyed by
registry key for ungrouped modules (`insights.overview` → chart, profitability
→ money, sales → funnel, cash → wallet, inventory → box, performance → people)
with `'panel'` as the fallback; six glyphs added to `Icon.tsx` where missing.
Collapsed rail shows the icon alone, like the divisions.

**7. Sales order delete says what blocks it.** Wrap the delete in
`deleteOrRefuse(order.number, …)` so a FK is a readable 400, and before it
name what stands on the order — invoices, invoice requests, commission
requests, purchase requests, orders, outgoing and pull-out slips, by number
and status — in one message ("… is kept — Invoice GT-INV-2026-0012 (CANCELLED)
and invoice request GT-IR-2026-0003 still name it; delete those first"). A
CANCELLED invoice/request/PO on a cancelled order goes WITH it in the same
transaction, each audited (the project's rule of 2026-10-19), when the owner
says so (question Q7). Cancel gains the invoice-request and commission-request
checks that pull-back already has. verify-sales: the message names the
blocker; a cancelled invoice goes with the order.

**4. Memos.**
- The register's switch reads **Drafted by me · All** (the label, not the
  key), and a recipient's own list is unchanged (My Records › Memos Received).
  A super admin's bare visit opens on All (already the default).
- **Pull back and delete an issued memo** (the issuer or Edit All):
  `POST /memos/:id/pull-back { reason }` → DRAFT, its recipients' rows kept
  with their acknowledgements (so a re-issue says who had already read the old
  text) or dropped — Q4a; every recipient told ("Memo … was withdrawn: reason");
  `DELETE` then takes a draft as today, or — Q4b — an issued memo directly,
  recipients told, one DELETED audit row naming how many had acknowledged.
- **Explanation letter**: `MemoRecipient.reply`, `repliedAt`, and
  attachments on `memo_reply` (entityId `<memoId>~<employeeId>`); `POST
  /memos/:id/reply { text }` — the recipient's alone, before acknowledging
  (a reply after acknowledgement is refused unless Q4c says otherwise), one
  reply editable until acknowledged; HR told (`memo.replied`), the reply
  shown under the recipient on HR's page and printed in the Acknowledgements
  table; the recipient's page gets a "Write an explanation" panel (in the
  page, never a dialog) beside Acknowledge.
- **The stamp**: the Acknowledgements table prints `formatDateTime` (date and
  time, Manila), and the recipient's own copy prints an "Acknowledged by
  <name> on <date, time>" line — the digital-signature wording the RFA uses.
verify-hr pins all four.

## The owner's answers (2026-10-21)

1. **PO label — "always the highest level of position (CEO), even if he also
   holds the level-2 Purchasing Manager for imports."** The rule to build: a
   slot prints the SIGNER's highest-level role (`titleFromRoles`, the title
   the system already keeps) when it outranks the step's role; the step's
   name otherwise. So Carter prints once as CEO / PRESIDENT on an importation
   order whatever the amount; a non-CEO import manager keeps "Purchasing
   Manager (Import)". `onePerPerson` on the PO and Incoming papers.
2. **Activity reason — yes**: required for Not going, optional otherwise.
3. **Assets — G-CORE tag numbers** (GT-AST-2026-0001). Cost kept, read by
   HR Edit All (unanswered; the assumption stands).
4. **Memos — delete only after pull-back** (an issued memo is pulled back to
   draft first; the acknowledgements already given are kept on the rows —
   unanswered, assumed). **A recipient who replied can still acknowledge**:
   the explanation letter never blocks the acknowledgement, and the reply is
   written before acknowledging.
5. **Hiring — print and sign only**: no online contract link this round (the
   hire has no G-CORE access yet). Section placement, the MPR and contract
   routes and the exam benchmark were not answered — build the assumptions
   (own "Hiring" section between Records and People; MPR Team Leader › HR
   Officer › CEO / President; contract Technical Manager › Team Leader › HR
   Officer › CEO / President; benchmark = average of hired candidates) and
   leave the routes editable in Admin › Approval Workflows.
6. **Sales order delete — what stands on it must be deleted first**: nothing
   goes with the order; the refusal names every record, live or cancelled,
   by number and status.
